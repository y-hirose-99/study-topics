### 1. `/code-review` で「PR を出す前のセルフレビュー」を定着させる（+ `/loop` で CI 見張り）— 18 点

- **概要**: Claude Code 2.1.328（2026-11-19）で、`/code-review` の指摘に Important / Pre-existing / Nit の重要度ラベルと修正案が付くようになった。`--fix` で作業ツリーに直接適用、`--comment` で PR にインラインコメントを投稿できる。2.1.329 からは、引数なしで実行するとブランチ全体をデフォルトブランチと比べてレビューする。ローカル版はどのプランでも使える。マネージド版（GitHub App）は Team / Enterprise で使え、Owner が有効化し、利用ごとに費用がかかる。後半では、PR を出した後に `/loop` で CI を見張る方法を 3 分だけ紹介する（critic の提案で P2 を吸収）。
- **15 分構成案**:
  1. （4 分）ローカル版 `/code-review` とマネージド版 Code Review の違い（費用・設定する人・起動するタイミング）
  2. （7 分）デモ: バグを仕込んだブランチで `/code-review` → 重要度ラベルを確認 → `--fix` で修正
  3. （4 分）チーム運用: プロジェクトのルールを CLAUDE.md に書く。おまけとして、PR を出した後に `/loop` で CI を見張る（セッションを開いている間だけ動く点は明示する）
- **想定対象者**: GitHub で PR を出す全員（モバイル / Web / インフラ）
- **注意点（critic 指摘）**:
  - デモに Flutter のリポジトリを使わない（過去テーマ「Claude を使った Flutter モバイル開発の実践」と見た目が重なるため）。Copilot と比べる構成にもしない（過去テーマ「乗り換え比較」と重なる）。
  - 「Important 件数で CI を止める」方法はマネージド版の check run 前提で、そのマネージド版の check run も failure では終わらない。ローカル版では使えない。
  - `/loop` の 30 日上限は 2.1.330 からで、条件付き。
- **根拠 URL**:
  - https://code.claude.com/docs/en/changelog （2.1.304 / 2.1.307 / 2.1.323 / 2.1.328 / 2.1.329 / 2.1.330）

### 2. Claude Code の許可確認との付き合い方: 対話は auto mode、無人は deny 設定 — 15 点

- **概要**: P3（`/auto-mode-setup`、`claude auto-mode critique`）と P4（無人実行の権限設定）を統合した枠。`/auto-mode-setup`（2.1.304、2026-10-19〜）は CLAUDE.md・git remote・最近のコマンドを読んで、信頼する範囲（`autoMode.environment`）の下書きを作る。無人実行向けには次の設定が使える。
  - `denyInsteadOfPrompting`（2.1.319）: 確認待ちを拒否扱いにする
  - `blockWritesOutsideWorkingDirectories`（2.1.314、2026-10-30）: 作業ディレクトリの外への書き込みを止める
- **15 分構成案**:
  1. （5 分）対話: `/auto-mode-setup` で信頼する範囲を教え、`permissions.ask` で push と PR 作成だけは人が確認する
  2. （6 分）無人: `denyInsteadOfPrompting` と `blockWritesOutsideWorkingDirectories` で「止まらない・はみ出さない」設定を実演する
  3. （4 分）確認: `/permissions` の Recently blocked と `claude auto-mode critique`。認証期限・MCP hook・`mcp add-json -` は補足スライド 1 枚にまとめる
- **想定対象者**: Claude Code を日常的に使う人、Claude Code を CI や定期実行で回すインフラ担当
- **条件・注意点（critic 指摘）**:
  - Team プランでは auto mode を組織単位でオフにできる。**社内で有効かどうかを発表前に確認すること**。
  - `autoMode` の設定はプロジェクトの `.claude/settings.json` からは読まれない。チームで共有するには managed settings（Owner が配布）が必要。
  - `blockWritesOutsideWorkingDirectories` の対象は Write / Edit / NotebookEdit。Bash 経由の書き込みが止まるかは未確認（推測）なので、settings-reference で確認すること。
- **根拠 URL**:
  - https://code.claude.com/docs/en/auto-mode-config.md
  - https://code.claude.com/docs/en/changelog （2.1.304 / 2.1.314 / 2.1.318 / 2.1.319 / 2.1.327 / 2.1.328 / 2.1.330）
- **スコア**: 新しさ 4 / 実務への効き 3 / 15 分で話せるか 4 / デモ映え 4 = **15**

### 3. CocoaPods trunk の read-only 化（12/2）: 社内 Flutter アプリで何が起きて何が起きないか — 13 点（条件付き）

- **概要**: Flutter 3.50（stable CHANGELOG に 3.50.0 / 3.50.1 を確認）と Dart 3.14.1（2026-11-17）が出た時期に重なり、CocoaPods trunk が 2026-12-02 に read-only になる予定と報じられている。**既存のビルドは壊れない**が、trunk への新しい pod・新しいバージョンの追加が止まる。そのため、依存プラグインが Swift Package Manager に対応しているかが今後の焦点になる。
- **15 分構成案**:
  1. （4 分）12/2 に何が起きて、何が起きないか（結論は「既存ビルドは通る」を先に言う）
  2. （7 分）デモ: 社内アプリの依存プラグインの SwiftPM 対応状況を一覧にし、SwiftPM を有効にして iOS ビルドする
  3. （4 分）今後の移行方針と、CI の macOS ランナーで気をつける点
- **想定対象者**: モバイル（Flutter）。インフラは iOS の CI を担当している人
- **条件・注意点**:
  - CocoaPods の 12/2 の日付は検索結果の要約しか確認できていない（blog.cocoapods.org は未取得）。**発表前に一次情報で裏を取ること**。
  - SwiftPM 有効時のビルド不具合が過去版の CHANGELOG に載っているので、デモのリハーサルは必須。Mac と Xcode が要る。
  - 「3.50 の新機能紹介」は未確認なうえ時間も超えるので含めない。
- **根拠 URL**:
  - https://raw.githubusercontent.com/flutter/flutter/stable/CHANGELOG.md （一次情報。3.50 のリリースを確認）
  - https://raw.githubusercontent.com/dart-lang/sdk/stable/CHANGELOG.md （一次情報。3.14.1 = 2026-11-17）
  - https://blog.cocoapods.org/CocoaPods-Trunk/ （未取得。日付は検索結果の要約）
- **スコア**: 新しさ 4 / 実務への効き 2 / 15 分で話せるか 4 / デモ映え 3 = **13**
